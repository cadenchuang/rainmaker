# Experimental live counting engine

`forecasting.counting.forecast(prior, state, created_at=..., config=...)` consumes
validated v2 `ElectionPrior` and `CountingState` objects and returns a
`CountingResult`. The result contains a `ForecastRecord`, integer final vote
vectors, corresponding reporting-group counted/outstanding vectors, all-candidate
pairwise share margins, eligible-candidate win probabilities, unresolved outcome
mass and effective empirical particle count. These probabilities describe this
experimental simulator, not calibrated election accuracy. No election-call or
trade authorization is produced.

## Counting model

- Each empirical particle is a complete local allocation paired with its original
  statewide turnout/support draw. Its starting probability is the local conditional
  weight divided by the number of statewide draws. Columns and groups are never
  independently resampled.
- Active materialized reports alone enter arithmetic. Raw cumulative reports,
  superseded editions and increment bases remain audit lineage. Constructors and
  a full contract round-trip validate corrections, numerical dependencies, source
  chronology, selected revisions, candidate ordering and disjoint coverage.
- Report geometry must be representable as a union of whole allocation cells.
  Statewide and mixed-method reports aggregate those cells. UNKNOWN method extent
  pools the unit across all methods, supplies a lower bound and cannot establish
  completion, even if the source labels its unresolved subset COMPLETE. A county
  report against a state-only allocation raises `ValueError`; it cannot justify
  invented county precision. Unsupported inputs are rejected before publication.
- A tempered multinomial score compares observed support with matching pooled
  local support. Unavailable candidate fields are excluded and the likelihood is
  conditional on the known candidate subset. It ignores turnout likelihood and
  caps evidence at 20 effective votes per group by default. A 25% original joint
  prior mixture remains after weighting. These choices limit, but cannot eliminate,
  bias from unrepresentative early batches. Different partition granularity can
  change the total effective evidence.
- Complete known-extent groups retain exact reported counts with zero outstanding
  votes. Other groups simulate final turnout around the selected prior turnout
  with shared and group lognormal shocks. Remaining turnout is the larger of the
  positive projected remainder and a half-normal tail with scale 5% of the larger
  of observed/prior group turnout. This heuristic retains a tail when a partial
  report exceeds every prior scenario; it is not a fitted completion model.
  Precinct/reporting-unit fractions and estimated completion percentages are never
  used as fractions of votes. Ballots cast describe counted accounting, not final
  turnout, and are never equated with valid contest votes.
- Missing candidate counts are imputed subject to known valid turnout. If only
  ballots cast are available, the residual valid total is uniform between the known
  candidate subtotal and the accounting upper bound after known non-contest votes.
  Without either total, a broad lognormal imputation extrapolates known support;
  with no positive known candidate votes it uses zero as the counted lower bound.
  This is weak identification and is always disclosed. Known observed values stay
  fixed; explicit zeros stay zero in the counted portion. Imputations never become
  likelihood evidence.
- Complete candidate vectors update support only in their own geographic/method
  group, with capped shrinkage (maximum 35%) toward observed support. Shared
  candidate and turnout shocks preserve cross-group residual dependence, on top
  of the intact empirical prior dependence. Unknown-method and ALL reports cannot
  teach separate method effects. The model makes no within-county precinct claim.
- Logistic-normal support is converted to integers by largest remainder; candidate
  index breaks ties. This is an approximate distribution of count vectors, not
  independent ballot-level sampling. Third parties retain their own columns and
  margins use all valid candidate votes. Ties have explicit unresolved probability.
  Any unresolved roster/write-in eligibility withholds all winner interpretation;
  numerical simulation draws remain available for research.

## Publication and replay

All newly generated bytes are returned in `result.artifacts`, keyed by SHA256.
Retain them alongside the upstream artifact/raw-byte store; the function performs
no filesystem writes or networking. The record itself is included as canonical
JSON. `result.simulation_artifact` identifies the supplemental group/final integer
output JSON and binds the exact record hash. Consumers must verify hashes before
reading. The existing contract cannot embed extra group-output fields; this
sidecar is deliberately outside the shared schema.

The run references the exact prior/state hashes, complete evidence catalog, raw
and lineage inputs, actual `created_at`, experimental counting model, configuration,
implementation bytes, contracts hash, exact Python/platform environment, sampling
procedure and RNG procedure bytes. Counting parameters are fixed heuristics, not
fitted estimates; the local model training manifest supplies their provenance
boundary, without claiming to fit a counting model on those examples. Model/run
identities change when their recorded computation time changes.

RNG v1 uses SHA256 counter midpoint uniforms and uncached Box-Muller normals in one
named stream. Constructor, seed expansion, spawn-key interpretation and draw order
are stored as content-addressed procedure bytes. The complete code defines branch
and tie order. Replaying the same inputs, config, computation timestamp, code and
recorded environment produces identical canonical records and sidecars. Floating
point transcendental operations require that environment for byte-exact replay;
integer conservation is exact. `replay(record, artifacts)` verifies the metadata
bytes and rejects unsupported RNG specifications, missing/corrupt artifacts or any
code/environment/procedure/output mismatch. Historical replay never changes receipt times.
The supplied timestamp must reflect the actual computation for a publication;
fixed synthetic timestamps in tests are fictional replay metadata.

Synthetic lineage forces SYNTHETIC (or WITHHELD) quality and research-only
eligibility. Real inputs remain EXPERIMENTAL, or DEGRADED for missing counts,
unknown method extent, incomplete turnout information, limited effective particle
support or unverified provenance. The engine never emits EVALUATED and does not
create evaluation reports. A separate historical evaluation of both statewide
and local performance is required before any accuracy claim. Prior support with
zero or very sparse scenario coverage remains a major limitation; residual noise
cannot repair a misspecified geographical model.

## Synthetic test invocation

From the repository root, with the repository test dependencies installed:

```sh
python -m pytest -q
PYTHONPATH=tests python -m unittest discover -s tests -p test_counting_engine.py -v
```

The tests use only the shared invented fixture elections. They cover both offices,
corrections, increments, overlap rejection, unknown turnout, missing candidate
counts, partial counties, known and unknown method coverage, misleading reporting
fractions, unrepresentative early batches, shared correlation, exact final counts,
ties, unresolved eligibility, integer conservation, artifacts and deterministic
replay. They establish software behavior, not forecast calibration.
